# ADR 0015 — Define progressive keyboard enhancements

## Context

mkpage currently ships semantic HTML/CSS that is usable without JavaScript. The
next step is to provide an optional keyboard-first enhancement layer for readers
who expect TUI-like movement while keeping no-JavaScript and native behavior
complete.

## Capability statement

mkpage should ship a small framework-free enhancement runtime that can be
globally enabled/disabled and that enriches only opted-in widgets through
explicit markup attributes.

## User stories / scenarios

- As a reader, I can move through list-like widgets with `j/k` and arrows and
  activate items without using a pointer.
- As a reader, I can use `g`-prefixed route shortcuts and get native browser
  navigation.
- As a reader, `/` opens a command surface and `?` opens contextual help.
- As a maintainer, I can keep JavaScript optional by letting core navigation
  continue to work when the runtime is absent.
- As a contributor, I can disable enhancements globally in site config.
- As a contributor, I can disable or remap behavior per widget with widget
  attributes.

## Acceptance criteria

1. Optional enhancement assets are emitted through mkpage and are cacheable,
   versioned, and framework-free.
2. Keyboard primitives include `j/k`, arrow equivalents, `Enter`, `Esc`, `/`,
   and `?` in opted-in widgets.
3. Shortcut capture is suppressed in editable and control-heavy controls.
4. Links remain native anchors; no JavaScript-only navigation path is required.
5. Route shortcuts are site-configurable and surfaced in help generated by the
   runtime.
6. Pointer and touch interactions update the same active-focus model used by
   keyboard interactions.
7. The runtime never applies global behavior to widgets without explicit
   enhancement attributes.

## Out of scope

- Search integration and indexing, which is tracked as a separate issue.
- A general SPA router or in-page application state model.
- Requiring JS for tabs, dialogs, or core content.

## Open questions

- Should mkpage add a schema for route-shortcut mappings or should this remain
  template/runtime driven in v0.1?
